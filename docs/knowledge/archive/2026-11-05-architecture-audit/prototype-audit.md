## What the prototype actually is

The extensive browser UI is real source, but all remote capabilities depend on the Claude Artifact runtime. `B.init` (2434–2439) requests `window.claude.use` capabilities `db`, `user`, `assets`, `sample`, and optional `downloads`. `B` is a useful migration boundary, not a production backend implementation. It exposes broad collection listeners, whole-document writes, client identity checks, client scoring, and client-driven account cleanup. The Flutter app currently renders the foundation status screen, not these workflows (`mobile/lib/src/app/forged_sent_app.dart`).

The prototype has **partial**, narrowly scoped local persistence: challenge proof blobs use IndexedDB `fs-proof` (5740–5760); theme, collapsed sections, celebration markers, meal expansion, and test date use localStorage. This must not be described as a durable workout outbox. `saveWkNow` (4703–4707) saves a whole workout and suppresses rejection; `loadWk` (4710–4717) turns read failure into an empty workout. Daily check-ins use in-memory optimistic updates and serialized writes (2706–2724, 3102–3122). These behaviors are precisely what production must improve.

## Seed/content reconciliation

- `tasks.json` still describes calories as “Meal log coming soon,” although the source contains full meal logging. Treat it as stale copy, not an absent feature.
- `devotionals.json` and dated `devotionals-2026-10-30.json` coexist with embedded DEVOS. Pick a versioned publication manifest and verify semantic/content diffs before declaring one authoritative. Do not silently replace seed content.
- `workout-meta.json` describes 365-day plans, 218 movements, equipment mapping, warmups, alternative logic and time budgets. Those are content design assertions; actual safety, timing, video availability and all mappings need tests/review.
- `weekly-challenges.json`, `movement-standards.json` and embedded CHAL encode product-sensitive scoring and standards. Port fixtures into proposed contracts; do not approve the scoring merely by reproducing it.
- `db-rules.json` is Claude capability configuration (e.g. `view`/`interact`/`owner`), not deployable Firebase rules. It does not establish production group isolation.
- `junior-challenges.json` is an adult-led activity content source in this prototype, not authorization to create youth accounts or process children's identities.

## Highest-impact defects to avoid inheriting

1. Whole-workout writes swallow failures; failed reads become empty sessions (4703–4717). Durable local state plus explicit failed/pending status must precede feature completion claims.
2. Broad listeners (`watchChecks` 2522, `watchAllChal` 2540, profiles 2601, teams 2571, all checks 10411) are not group isolation. Production queries need scoped paths and matching server rules.
3. Client `pointsOf`, `chalStandings`, `campStandings`, `awardPRs` and referral attribution must never set trusted competition results.
4. Check-in document fields include fasting, protein bonus, steps and optional-day notes (2528). These can reveal sensitive health/religious behavior even without raw meals. Define approved group projection explicitly.
5. Client `deleteMyData` covers many paths but does not visibly delete weights, onboarding/seen, challenge submissions, team membership/team posts or all associated derivatives (2620–2640). Production deletion requires a complete inventory and retryable server job.
6. Native health, notifications, RAG and real identity/authorization are not established by the browser UI or a local mock.
7. Prototype prayer-at-start and scroll-to-complete details need accessibility and optional-prompt decisions; neither should gate safe exercise or create spirituality-quality scoring.

## Dependency ordering for parity

Content versioning + identity + private ownership → durable local event transaction → workout/devotional first slice → retry/idempotent server receipt → daily progress/history → group membership and explicitly approved public projection → trusted scoring → challenges/boards → campaign/team lifecycle → community/moderation. Private nutrition can proceed after private storage and goal-policy approval, independently of competition. AI, automatic health imports and youth-related behavior remain later explicit gates. Media durability/storage rules are prerequisites for progress photos, proof and community attachments, not follow-up cleanup.
