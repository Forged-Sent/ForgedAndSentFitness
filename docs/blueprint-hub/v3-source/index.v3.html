Build the real house from the sketch.

Forged & Sent is a faith-centered devotional workout and brotherhood platform. The production app is being built in Flutter on Firebase. The prototype keeps its content and its lessons. This page records every decision, how each one was reconciled with the approved direction on 27 Oct, what is still open, and what each of us thinks.

Think of the prototype as a detailed sketch of a house that people have already lived in for a few days. We keep the furniture (the content and the lessons learned) and pour a real foundation on Firebase: private prayers and health data stay private, devotions and workouts fit together however each man prefers, and only the referee writes the score.
Reconciled 27 Oct 2026

Each of the 35 decisions now carries its reconciliation with the approved direction: Aligned, Improvement, Conflict (resolved in favor of the approved direction), Open (needs a human decision) or Superseded. Changed recommendations: Firebase (D03), integrated devotional workouts (D08), participation-only faith points (D09), configurable video proof (D18–D19), two difficulty tiers (D20), team-first boards (D24), practice seasons (D27), bounded nutrition points (D30), Crashlytics (D35). What works without signal

  • Viewing downloaded programs and today's devotional
  • Running a whole workout: sets, reps, weights, rest timers
  • Habits, water, meals, private reflections
  • Recording a challenge attempt (it's submitted when back online)
  • Your own history

Needs signal: final rankings, proof review, invitations, account deletion. A proof video recorded offline waits on the phone and uploads later.

Minimum security before the first release

  • Deny-by-default security rules, tested for every role
  • Phones never write points; only Cloud Functions do
  • Proof videos never use shareable download links
  • Private photo storage; location data stripped from photos
  • Complete account deletion and data export
  • No private text in notifications
  • Report → review → action loop; blocking enforced on the server
  • 18+ age check; backups with a tested restore

How Firebase keeps scores honest and data private

Firebase was the approved choice. The independent review had worried about fair scoring and privacy across groups, so each risk has a Firebase control. Phones can only add facts ("I did this"), never points. Only Cloud Functions write the ledger, and every entry has a fixed id, so retries can't double count. Security rules deny everything by default and are tested for every role on every change. Daily exports protect against data loss.

How a challenge moves through its life

Draft → Scheduled (rules locked) → Open → Closed → In review (leaders check proof) → Finalized (results locked with a fingerprint) → optional Appeal → re-finalized with an adjustment that records who changed what and why.

Why retries can't double count

Every check-in or attempt gets a unique ID on the phone. If it's sent twice because signal dropped, the server sees the same ID and files it once. Points are written as ledger lines keyed to that ID and rule version, so they can't be duplicated either.

Discipleship

A daily rhythm, not a points box

The aim is that a man meets God in Scripture, responds honestly, prays for his brothers and does one concrete thing, with a brother walking alongside him. He chooses when: before his workout, after it, in short prompts during rest, or at separate times of day. His private prayers and reflections are never a contest.

What could go wrong

Top risks found in the prototype

#SeverityRiskIn plain words
Data model

Who sees what

Every piece of information has a privacy level, chosen ahead of time: private (only you), partner, leaders, or group. Health, weight, photos, food, fasting, prayers and reflections are private unless you choose to share. Being in the same household never unlocks anything.
LevelExamples
PrivateReflections, food and water, fasting, weight and measurements, progress photos, health data, your program settings, personal habits
PartnerAccountability check-ins; prayer requests if you choose
LeadersChallenge proof, reports, overall devotional participation (not per man); prayer requests if you choose
GroupName and photo, posts and comments, workout summaries, scored check-ins, the board; prayer requests if you choose

Records that never change

Check-ins, challenge attempts, completed devotionals and score ledger lines are never edited. Corrections are added as new entries with who and why, so history and results can always be rebuilt and checked.

When someone deletes their account

Everything they own is deleted, including their photos. Their posts in the group show as "former member". Locked past results keep an anonymous row so the standings still add up.

How we build

Two developers plus AI tools

AI coding tools are fast helpers, but helpers working at the same time can undo each other. There is a catalog of eight specialist roles, and only two to four work on any one change. Each helper gets a clear room to work in, and the blueprint has one guard who checks every change.
Reviewer · read-only

Architecture reviewer

Checks changes against the decisions on this page and the code layout rules. Flags conflicts to humans; never resolves them.

Reviewer · read-only

Security & privacy reviewer

Runs the lock tests and checks anything touching prayer, health, photos, deletion or notifications.

Writes tests only

Test engineer

Fills missing tests after a change. If a test finds a bug, it reports it rather than fixing app code.

Rules every agent follows

  • One requirement per change, small enough to review (about 400 lines)
  • Database design, scoring rules and content approvals are protected zones: two human approvals, plus an automatic guard
  • AI never approves theology or merges code
  • The same instructions and skills for Claude Code and Codex: add a feature, change Firestore or the rules, change scoring rules, validate content, handle proof media, review architecture, review security
  • Roles: Flutter implementer, Firebase backend, content engineer, release engineer (builders); architecture, security and faith-content reviewers (read-only); test engineer (tests only)
