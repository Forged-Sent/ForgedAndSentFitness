# ADR-0005: Flutter state, navigation and durable local storage

- Status: **Accepted dependency direction; implementation pending**
- Date: 2026-11-08
- Decision owner: project maintainer (accepted the Riverpod/go_router/Drift direction in the Codex conversation on 2026-11-08; publication PR pending)

## Context

The production Flutter client is still a foundation scaffold. It needs independent Android/iOS development, owner-only offline completion, durable workout events and eventual idempotent sync. Firebase's local cache is not the durable event record. [ADR-0001](ADR-0001-mobile-foundation.md) and [ADR-0002](ADR-0002-emulator-first-firebase.md) remain authoritative for privacy, backend and emulator boundaries. The current package and SDK evidence is in the [research note](../knowledge/archive/2026-11-08-flutter-stack/research.md).

## Decision

1. Use **Riverpod** for Flutter presentation state and composition. Start with manually declared providers, a single app `ProviderScope`, and provider overrides in tests; do not add a separate service locator or a second state-management framework. Views observe state and send actions to view models. Domain and application services remain plain Dart with constructor-injected repository interfaces. Riverpod is not the durable event store. Flutter's [architecture recommendations](https://docs.flutter.dev/app-architecture/recommendations) support the view/view-model/repository split; Riverpod's [testing guide](https://riverpod.dev/docs/how_to/testing) documents provider overrides.
2. Use **go_router** for app navigation and deep-linkable route structure, with route configuration outside feature widgets. Route redirects may guide sign-in UI but never authorize group or private data access; that belongs to server-enforced rules. Flutter [recommends go_router for most apps](https://docs.flutter.dev/app-architecture/recommendations). Native deep links remain unverified until reviewed Android/iOS hosts and device tests exist.
3. Use **Drift with native SQLite** for locally durable completion events and an outbox on Android/iOS. The event ID is stable for one logical action and unique in local storage. Write the event and derived local state in one transaction before any sync attempt; keep pending work through app restart. Use `drift/native.dart` with a background database and `path_provider` for an app-owned path; use `drift_dev` and `build_runner` for generated schema code. [Drift's native guide](https://drift.simonbinder.eu/platforms/vm/) describes native library loading for current versions; the implementation PR must prove that its resolved package graph and actual Android/iOS builds supply SQLite without the deprecated convenience-package dependencies. [Flutter's offline-first guide](https://docs.flutter.dev/app-architecture/design-patterns/offline-first) supports this boundary. Server deduplication, conflict handling and sync receipts require a later backend contract and tests.
4. Keep web as a clearly labeled development preview. A web fake may render the first screen, but must not claim durable saves or cloud sync. Drift web persistence requires a separate [WASM and worker setup](https://drift.simonbinder.eu/platforms/web/) and browser tests before a web durability claim. Desktop support remains proposed under [ADR-0003](ADR-0003-flutter-targets.md).

The package families are approved here. go_router was added at exactly 18.1.4 in build step S0, for the tab shell; Riverpod and Drift are **not yet added** to `mobile/pubspec.yaml`. Choose exact compatible versions in a focused dependency/first-slice PR, commit the lockfile and generated schema, and validate the agreed SDK across Windows, macOS and CI. Current CI pins Flutter `3.47.8`. This Windows machine's default Flutter is `3.44.8` / Dart `3.12.2`, while the committed lockfile requires Dart `>=3.13.0`; a separate Flutter `3.47.8` / Dart `3.13.7` checkout now passes the scaffold tests without changing the lockfile. Dependency work must use that pinned SDK explicitly (see the [CLI guide](../development/FLUTTER-CLAUDE-CLI.md)), and Mac/CI behavior still needs its own verification. Current [pub.dev version tables](https://pub.dev/packages/flutter_riverpod/versions) show latest Riverpod requires Dart 3.12; [go_router](https://pub.dev/packages/go_router/versions) requires 3.12 and [Drift](https://pub.dev/packages/drift/versions) requires 3.10. Do not broaden platform claims from package metadata alone.

## Alternatives and consequences

- `ChangeNotifier` plus `provider` would use Flutter's recommended baseline with fewer moving parts, but Riverpod's override and async-state model better fits the planned offline/retry flows. This is a project choice, not a Flutter requirement.
- `Navigator` alone works for a small screen count; go_router provides a stable route boundary before sign-in and deep links grow.
- `shared_preferences` is unsuitable as an ordered, transactional event outbox. Raw `sqflite` could work but would make schema, migrations and typed query checks mostly hand-written. `drift_flutter` is convenient but its [current published dependency list](https://pub.dev/packages/drift_flutter) includes two end-of-life SQLite library packages; direct native Drift avoids them.
- Code generation, schema migrations and native database lifecycle add build work. The first implementation PR must prove duplicate-event idempotency, close/reopen durability, migration behavior, provider overrides, widget navigation and an Android build. An iOS simulator build requires macOS. No local test alone proves cloud sync or server authorization.

The first feature should use synthetic devotional/workout content, owner-only progress and honest local pending states. No private prayers, injuries, measurements, scoreboards or production Firebase writes are enabled by this ADR. Sign-out retention and sensitive-field encryption need separate maintainer decisions before such data is stored.
